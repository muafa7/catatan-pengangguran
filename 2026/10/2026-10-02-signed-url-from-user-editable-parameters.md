# From User-Editable Parameters to Signed URLs

Today I learned why data coming from a URL should never automatically be considered trusted.

I had a feature where some values were passed directly through query parameters.

Conceptually, it looked like this:

```text
/resource?value=100&name=example
```

It worked, but there was an obvious problem once I looked at it from the user's perspective:

**the user controls the URL.**

They could simply change:

```text
value=100
```

into:

```text
value=999999
```

Even if my frontend never provides a UI for changing that value, the browser is still controlled by the user.

That means:

```text
Data generated by frontend
≠
Trusted data
```

## The Problem With Raw Query Parameters

Suppose the application generates:

```text
/resource?value=100
```

The backend receives:

```text
value = 100
```

But there is no proof that `100` is actually the value originally produced by my application.

The user could manually request:

```text
/resource?value=500
```

From the backend's point of view, both requests are just user input.

So I needed a way for the backend to answer:

> Is this the same data that my application originally issued, or has somebody modified it?

That led me to signed URLs.

## Moving to a Signed URL

Instead of exposing trusted values directly:

```text
/resource?value=100&name=example
```

the URL can contain a signed token:

```text
/resource?token=<SIGNED_TOKEN>
```

Conceptually, the token contains two parts:

```text
payload.signature
```

The payload contains the data I want to protect from modification.

For example:

```json
{
  "resourceId": "abc123",
  "value": "some-data"
}
```

The exact fields are not important.

The important part is that the payload is signed by the backend.

## Encoding the Payload

First, the payload can be serialized and encoded.

For example:

```ts
const encodedPayload = Buffer.from(
  JSON.stringify(payload),
).toString('base64url');
```

This produces something that is easier to place inside a URL.

But one important lesson:

```text
Base64URL is not security.
```

Anyone can decode Base64URL.

Its purpose here is only to represent the data in a URL-friendly format.

## Signing the Payload

The backend can then generate a signature using HMAC-SHA256.

Conceptually:

```text
signature =
HMAC-SHA256(
    encodedPayload,
    SIGNING_SECRET
)
```

In Node.js:

```ts
const signature = crypto
  .createHmac('sha256', SIGNING_SECRET)
  .update(encodedPayload)
  .digest('base64url');
```

Then combine them:

```ts
const token = `${encodedPayload}.${signature}`;
```

The final URL becomes something like:

```text
/resource?token=eyJyZXNvdXJjZUlkIjoiYWJjMTIzIn0...
```

## What Stops Someone From Modifying It?

Technically, nothing stops the user from editing the token.

They control their browser.

They could decode the payload, modify it, and encode it again.

For example:

```text
Original:

value = 100
```

changed into:

```text
Modified:

value = 999999
```

But changing the payload causes another problem for the attacker.

The original signature was generated from:

```text
original payload
+
secret known only by backend
```

After changing the payload, the old signature is no longer valid.

The attacker would need to generate:

```text
HMAC-SHA256(
    modifiedPayload,
    SIGNING_SECRET
)
```

But they do not know `SIGNING_SECRET`.

So they cannot create the correct signature.

Conceptually:

```text
ORIGINAL

Payload
   ↓
HMAC + Secret
   ↓
Signature A

Payload + Signature A
   ↓
VALID
```

But after modification:

```text
MODIFIED

Modified Payload
   +
Signature A
   ↓
Backend recalculates signature
   ↓
Signature B

Signature A != Signature B
   ↓
REJECT
```

That was the part that made signed URLs click for me.

## Verification on the Backend

When receiving the token, the backend separates the payload and signature.

```text
encodedPayload.signature
```

Then it calculates the expected signature again:

```ts
const expectedSignature = crypto
  .createHmac('sha256', SIGNING_SECRET)
  .update(encodedPayload)
  .digest('base64url');
```

The backend compares:

```text
received signature
        vs
expected signature
```

If they match, the payload has not been modified since it was signed.

If they do not match, the request should be rejected.

For cryptographic signature comparison, Node.js also provides:

```ts
crypto.timingSafeEqual()
```

which is preferable to treating the signature as an ordinary string comparison.

## Signed Does Not Mean Encrypted

This was another important thing I learned.

A signed payload can still be readable.

Suppose the token contains:

```json
{
  "resourceId": "abc123",
  "value": "some-data"
}
```

Someone may still be able to Base64URL-decode the payload and see those values.

Signing protects:

```text
Integrity
```

It answers:

> Has this data been modified?

Encryption protects:

```text
Confidentiality
```

It answers:

> Can somebody read this data?

And encoding is something different again:

```text
Encoding
    ↓
Changes representation

Signing
    ↓
Detects modification

Encryption
    ↓
Hides information
```

For my case, my problem was data integrity.

I needed to detect whether values had been changed.

So signing was the relevant mechanism.

## Before

My previous mental model was roughly:

```text
Frontend creates URL
        ↓
/resource?value=100
        ↓
Backend reads value
        ↓
Use value
```

The problem:

```text
Frontend creates URL
        ↓
User modifies URL
        ↓
/resource?value=999999
        ↓
Backend receives 999999
```

The backend has no way of knowing that the original value was different.

## After

With a signed token:

```text
Backend-approved data
        ↓
Create payload
        ↓
Sign payload using secret
        ↓
payload.signature
        ↓
Send through URL
```

When it comes back:

```text
Signed Token
      ↓
Separate payload + signature
      ↓
Generate expected signature
      ↓
Compare signatures
      ↓
Valid?
  ┌───┴───┐
  │       │
 YES      NO
  │       │
Decode   Reject
payload
```

Now the user can still modify the request, but they cannot silently modify the trusted values.

## The Secret Is the Important Part

The security of this approach should not depend on hiding:

```text
HMAC-SHA256
```

or hiding the fact that the application uses:

```text
payload.signature
```

Those mechanisms can be known publicly.

What must remain secret is:

```text
SIGNING_SECRET
```

Knowing the algorithm does not give someone the ability to generate a valid signature.

Without the signing secret:

```text
known payload
+
known algorithm
+
unknown secret

=

cannot generate valid signature
```

This is also why the signing secret should stay on the backend and should never be exposed to frontend JavaScript.

## Don't Put Secrets in the Payload

Another thing worth remembering:

The payload itself should not contain secrets.

A signed payload may be readable.

So this would be a bad idea:

```json
{
  "apiKey": "...",
  "password": "...",
  "secret": "..."
}
```

Signing does not make those values private.

The payload should contain only information that is acceptable to expose to whoever receives the URL.

## What I Learned

The biggest lesson was not really about HMAC.

It was about the trust boundary between the frontend and backend.

Before:

```text
"The frontend generated this value,
so I can trust it."
```

Now:

```text
"The client controls the request,
so the backend must verify anything
that needs to be trusted."
```

And signed URLs are one way to handle situations where I want to send data through a client-controlled environment while still being able to detect modification.

The simplest way I now think about it is:

```text
Normal parameter

value=100
   ↓
User changes it to 500
   ↓
Backend cannot detect where 500 came from
```

versus:

```text
Signed data

value=100
   ↓
Backend signs it
   ↓
User changes it to 500
   ↓
Signature becomes invalid
   ↓
Backend detects the change
```

So a signed URL does **not** make data uneditable.

It makes unauthorized modifications **detectable**.

That distinction is what I want to remember.
